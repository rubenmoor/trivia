# 14 — Input: Mouse, Controller, Couch Co-op

**Status:** draft

Part of the Steam plan ([11](11-steam.md)). The keyboard keys shown on the buttons (`A`–`D`, `1`–`4`, the joker letters, `Enter`, `Esc`) are good and stay. Three steps follow, in this order.

## 1. Everything clickable (now)
Every action that has a key must also have a visible control that works with a mouse click or a touch tap. The key chip on a button doesn't change; it is a hint, not the only way.
- Audit: every `keydown` branch in `app/client/src/game/Game.svelte` (Start `N`, Select `1`–`4`, `Enter`/`Space` to continue, `Esc` overlay) and the dialogs (Paso, Cambiazo picker, Francotirador aiming, `Backspace` = back/cancel, the arming timeout).
- Missing today: likely «continue» on Level/Correct screens (it is `Enter`/`Space`), `Esc` for the overlay (needs a small, unobtrusive menu button in a corner), and `Backspace` in dialogs (needs a visible «Atrás»/«Cancelar»).
- Rule for new UI from now on: no action without a clickable control (add to `04-ui-tv-display.md`).

## 2. Controller support (S3)
**How it works:** the browser [Gamepad API](https://developer.mozilla.org/docs/Web/API/Gamepad_API) works in Chromium, and so inside Electron (18). With the "standard" mapping, Xbox-style controllers show up the same everywhere. On Steam, **Steam Input** translates almost every controller (PlayStation, Switch, Steam Controller, the Deck's own controls) into a virtual Xbox controller by default. So the game only needs to handle one layout. There is no need to talk to the Steam Input API at first.

- **An action layer** between devices and screens: `confirm`, `back`, `menu`, `answer(1..4)`, `joker(name)`, `navigate(direction)`, `peek` (hold). The keyboard, mouse and gamepad all produce these actions; screens listen only to actions. This replaces the key handling scattered in `Game.svelte`.
- **Peek** (plan 113, decision 126): the one hold action, `{ type: "peek", down }`: press → down, release → up (key `keyup`, pad release edge in `step`); every other action is a press edge. Safety release on window `blur`, hidden page, inactive pad loop, pad disconnect, modal scope push. Only on the Question screen of a sharp image question (04 "Question").
- **Focus navigation:** with a controller, the D-pad / left stick moves a visible focus ring (the sky-blue focus of D-29) between buttons; `A` = confirm, `B` = back, `Start` = menu.
- **Direct buttons** (pm decision 9): on the Question screen `Y`/`B`/`X`/`A` pick answers by position (top-left, top-right, bottom-left, bottom-right; tiles get a glyph next to the letter), `RT` submits, `LT` unlocks, `R3` (hold) peeks at the picture, key per catalog `screen.question.peekKey` (`V` in es, es-ES, en, de); `LB`/`RB` move focus through the joker tray, where `A` arms and plays, `B` disarms. Per-scope pad map: `Scope.pad` in `lib/input.svelte.ts`.
- **One player, every device** (plan 156, milestone 8): every pad, the keyboard and the mouse drive the same player and replace each other at any moment, no switching step (per-device players in a local multiplayer session: section 3).
- **Glyphs:** button prompts follow the last input, on every screen and in every mode. Keyboard press, mouse move (≥ `MOVE_PX` of real travel, synthetic moves ignored) or click → key prompts. Any pad input → glyphs: a press edge of any button, mapped or not, or either stick pushed past the dead zone from rest (idle drift never switches). A control without a pad binding shows no glyph in pad mode. The right stick only switches (decision 272), R3 stays the peek. Glyph set: keyboard letters, Xbox glyphs, or PlayStation glyphs (from `Gamepad.id`; under Steam (SW-8, task 649) Steam Input's `GetInputTypeForHandle` of the connected pads: all PS3/PS4/PS5 → PlayStation, else the pad's own `Gamepad.id`, which under Steam Input is the virtual Xbox pad; per pad, `styleFor` in `lib/gamepad.svelte.ts`). The glyph art must be original or from a free set (17).
- **Polling:** the Gamepad API has no events for buttons, so poll it with `requestAnimationFrame` while a gamepad is connected.
- **Steam Deck:** 1280×800 (16:10), built-in controls = gamepad. Deck Verified requires full controller support, readable text and no keyboard needed except for text entry, which means the **player name** needs the on-screen keyboard (Steamworks `ShowFloatingGamepadTextInput`, 18) or an in-game letter picker. *S3: in-game letter picker, plan 46 (`LetterPicker.svelte`, shown only for a pad; 04 "Player"); S5 (SW-8, task 648): under Steam in Big Picture or on the Deck, A on the field opens `ShowFloatingGamepadTextInput` at the field (keystrokes into the focused `<input>`); elsewhere the letter picker; `ShowGamepadTextInput` only if the developer check (task 652) finds keystrokes don't reach Chromium. Screen check at 1280×800/720 done (SW-4, 18): text ≥ 9 px incl. pad glyph labels; real-Deck check in plan 48.*

## 3. Multiplayer input
Local multiplayer ([13](13-game-modes.md), milestone 16: `Local multiplayer: game modes and controls`) gives every player their own controls on the one machine; no phones, no LAN server (D-77). Before a session starts every device drives the shared UI, as in section 2; once it runs, only the player whose input it is acts. Built in plan 161: `Per-player controls`; it supersedes decision 24: `Multiplayer input and couch co-op (OQ-37)?` where they differ.
- **Seats** (`lib/seats.ts` pure, `lib/seats.svelte.ts` state): every action carries its `Source` (`{ pad: index }`, `"keyboard"`, `"mouse"`; `device` stays for prompts and mods). A seat's `Binding`, join order: `{ pad }`; `"kbm"` (keyboard and mouse together, exactly one once a pad has joined, decision 274); `{ key }` (keyboard-only `timed`: a claim key per player); `"shared"` (keyboard-only round-robin: keyboard and mouse act for the turn, a player's own key does nothing, decision 273).
- **Binding lifetime:** the join screen sets it at session start (`bindSession`), in `sessionStorage` by game id for a reload; Game.svelte's `watchGame` turns the filter on for a running session row and ends it with the session; a reload without the stored binding leaves every seat unbound (rebind: decision 289). No device in the save (decision 277).
- **Who acts:** `seatOf(source, intent, view)`: a pad → its seat (unbound → none); keyboard and mouse → the `kbm` seat, else a claim's key seat, the claimer (`timed`) or the turn seat. `may(seat, view)`: round-robin the turn seat; `timed` any seat still in, once claimed only the claimer; out seats never.
- **Filter** (`gate` in `lib/input.svelte.ts`): outside a session every device acts. In one, `menu` always passes (decision 288); a scope marked `shared` takes every device, with everything opened above it (Esc menu, flag dialog, Wrong/Victory/Completed); else only a seat that may act. Dropped input does nothing: no sound, no focus move, no prompt switch. Mouse: a capture-phase `pointerdown`/`click` listener drops clicks of a keyboard-and-mouse seat that may not act; `[data-shared]` controls (the corner menu button) and a pad confirm's `el.click()` pass.
- **Acting seat:** `acting.seat` is set while an accepted action or click runs; `hooked` in `lib/api.ts` puts it into every game action's body (`seat`), else the turn seat or the claimer for an action after an await; the engine's `not_your_turn`/`not_your_claim` stay the backstop.
- **Prompts:** follow only input that may act (and plan 156's pad touch of such a pad); `seatDevice(seat)` gives a seat's device and glyph set (turn banner, claim prompts).
- **Join helpers** (plan 162: `Mode row, session setup and join screen`, decision 292): `joinPad` (an unbound pad's A; a lone keyboard seat becomes `kbm`; refused with two or more keyboard seats), `joinKeyboard`, `unboundPad` (also the lost-pad rebind), `claimKeyOk` (`game/question/keys.ts`, decision 290: one letter or digit no Question key, not 1–9 or the flag key, distinct).
- **`timed` claim** (decision 290; task 1433): intent `claim` (`key` for a key seat). `claimInput()` (`lib/seats.svelte.ts`) gives the timed question scope its `keys` and `pad`: LB/RB (`CLAIM_PAD`, `lib/gamepad.ts`; no jokers in timed), Space for the `kbm` seat (a scope key beats Space's confirm), each picked key for its `{ key }` seat (`claimKeys`, `lib/seats.ts`; `seatOf` maps the key to that seat); a click on a `[data-claim]` control is the `kbm` seat's claim through the mouse filter. An accepted claim calls `gameAction("claim")` with `acting.seat`; `may` lets any seat in claim while no claim is open, then only the claimer. After a claim the claimer answers with face buttons, A–D/1–4 or a click (decision 275), no new bindings. `claimLabel(seat)` (`lib/gamepad.svelte.ts`) is the prompt: bumper buttons plus the pad's glyph set, «Espacio» (`picker.space`) or the key. The scope itself comes with `plan 164: Timed game screens, drama and sound`.
- **Lost pads and the Esc menu** (decisions 288, 289, 282; task 1434): any seat's `menu` opens the Esc menu, a `shared` scope while open (`Overlay.svelte`); the corner button is `[data-shared]`. In `timed` opening it pauses the clock: `holdPause` (`lib/pause.ts`, refcounted: `pause` on the first hold, `resume` on the last release; nothing outside `timed`), released on close or when an action leaves the menu. `gamepaddisconnected` unbinds the pad's seat (`unbindPad`). `lostSeat()` names the seat that needs a pad: round-robin the turn seat, `timed` the first seat still in, at once; a seat that is out never asks. Then `SeatLost.svelte` (a `shared` modal under the Esc menu, strings `seat.*`) shows «Mando de <name> desconectado», holds the pause, and `menu` still opens the Esc menu; A on a pad bound to no seat (`unboundPad`) takes the seat (`rebindSeat`, stored in `sessionStorage`). After a reload without the stored binding every seat is unbound, so the dialog asks per seat in turn (keyboard seats too: a pad takes them; the Esc menu ends the session).
- **Findings (plan 161, task 1431; Chromium source and docs, no pads in a worker, so nothing measured here):**
  - Cap: `navigator.getGamepads()` has `Gamepads::kItemsLengthCap` slots, nulls for empty ones. Electron 43.7.7 ships Chromium 150.0.7871.250: cap 4 (Chromium main has raised it to 8, not in our version). A fifth pad is not listed: with 4 pads, keyboard and mouse is the only fifth player. The join screen takes every listed pad; no cap of our own. Windows backends (XInput, WGI, Raw Input) all fill the same 4 slots; no extra pads beyond.
  - Identity: a pad keeps its `index` while connected; the slot is found by (source, source id), else the lowest free slot. After a disconnect the slot is free: a pad connecting later takes the lowest free slot, so a returning pad may get another `index` when another pad connected meanwhile. Binding is by index, with `gamepaddisconnected` freeing the seat (decision 289: `Local multiplayer: a controller lost mid-session waits for a controller to take the seat`); a reconnecting pad is rebound by A, never assumed. `Gamepad.id` is the same string for the same model, so it doesn't tell two identical pads apart.
  - Per-pad style: `steam:input-types` in the shell lists `getConnectedControllers()` in Steam's handle order, which is not tied to `Gamepad.index`; the shell's Remote Play probe logs `getGamepadIndexForController(handle)` (Steamworks `GetGamepadIndexForController`, an XInput index, not a Chromium slot). So the set of types is reliable, a per-pad style by handle is unproven until the developer's check. Rule: `padStyleOf(index)` is `styleOf(Gamepad.id)` (Under Steam Input the id is Steam's virtual Xbox 360 pad, so Xbox glyphs); the Steam set decides only when all pads agree (`steamStyle`), as today.
  - Open for the developer's hardware (`decision 310: Pad measurements on real hardware: how many pads, in which order, with which style?`, once): Windows pad count and slot order, Steam Input on/off, handle ↔ index mapping, Deck's built-in pad.
- **Remote Play Together:** Steam streams the game to remote friends and their input arrives as extra virtual controllers, so it works for free once local multi-controller input works.
